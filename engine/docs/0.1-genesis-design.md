# Albatross 0.1 "Genesis" — 설계 기록

범위: Chess Core(Bitboard, Position, Move, MoveGen, Attacks, Zobrist, Perft)와 최소 UCI.
탐색·평가는 0.2 이후. 아래는 **구현된 결정**과 그 이유다.

## 1. 아키텍처

```
engine/src/core   types, bitboard, attacks, zobrist, move, position, movegen, perft   (다른 모듈에 의존하지 않음)
engine/src/uci    UCI 프런트엔드 (core 에만 의존, iostream 주입 → 단위 테스트 가능)
engine/src/main   uci 루프 + `albatross perft N [fen]`
engine/tests      의존성 없는 자체 테스트 하네스 (CTest 로 실행)
```

원안 대비 변경: `attacks` 를 `bitboard` 에서 분리하지 않고 별도 파일로 둔 점은 원안과 같고, `init.h`(idempotent
초기화), `perft.h`(core 안에 위치: UCI·테스트·CLI 가 공유)를 추가했다. `search/`, `eval/` 는 해당 버전에서 생성한다.

## 2. Square / Bitboard
- **LERF**: A1=0 … H8=63. 시프트 방향 상수가 단순(`+8` 북쪽)하고 `lsb`/`pop_lsb` 순서가 a1→h8.
- `Bitboard = uint64_t`; `popcount`/`lsb` 는 `<bit>`(C++20)로 이식성 확보.
- 대안(Rank-File 역순 등)은 이득이 없어 채택하지 않았다.

## 3. Piece / Color / Square
- `Piece = color*8 + type` (WHITE: 1–6, BLACK: 9–14). `color_of`/`type_of` 가 시프트/마스크 한 번이다.
- 열거형은 unscoped `enum : int`에 연산자 오버로드를 최소로 제공(Square ± int).

## 4. Move: 16비트 (from 6 · to 6 · flag 4)
- flag: quiet, double push, 두 종류의 castling, capture, ep, 승급 4종, 승급+캡처 4종.
  `flag & 4` = 캡처, `flag & 8` = 승급, 하위 2비트 = 승급 기물.
- 32비트 대비 이득: TT·무브 리스트·히스토리 테이블 캐시 효율. 손실: 정렬 점수를 못 담음 → 탐색 단계에서
  `ScoredMove{Move, int}` 로 별도 보관한다.
- `0` (a1a1 quiet)은 불가능한 수라 "수 없음"으로 겸용.

## 5. Position
`board_[64]`, `byType_[7]`, `byColor_[2]`, `stm_`, `gamePly_`, `vector<StateInfo>`.
`StateInfo`: `key, checkers, move, captured, ep, castling, rule50`.
mailbox + bitboard 이중 표현: 기물 조회 O(1) (캡처 판정·make/unmake)과 집합 연산(공격/무브젠)을 모두 빠르게 한다.

## 6. Make / Unmake
- `do_move` 는 이전 `StateInfo` 를 복사해 갱신 후 push, `undo_move` 는 pop 후 보드만 역방향으로 되돌린다.
  보드 변경은 복원이 필요 없는 값(키, 캐슬링, 50수 등)을 StateInfo 에 맡기므로 undo 가 단순하다.
- 대안(copy-make: Position 전체 복사)은 구현이 쉽지만 NNUE accumulator 등 상태가 커지면 비용이 크다.
- 검증: 트리를 순회하며 모든 do/undo 후 FEN·키·비트보드 동일성, 매 do_move 후 증분 키 == 재계산 키.

## 7. Castling / En Passant / Promotion
- **캐슬링**: `Castle.mask[sq]` 를 from/to 에 AND 하는 방식(기물이 움직이거나 잡히면 권리 소멸). 생성기는 경로가
  비었는지만 보고, 킹이 체크 중이거나 통과/도착 칸이 공격받는지는 `legal()` 이 판단. FEN 로드 시 킹/룩이 제자리에
  없는 권리는 조용히 제거.
- **앙파상**: FEN 방식으로 더블푸시 때마다 `ep` 저장(FEN 왕복 일치). 해시에는 *실제로 잡을 폰이 있을 때만* 섞는다
  → 같은 보드가 같은 해시를 갖는다. 제거할 폰 위치는 `to - push` 이고, 합법성은 점유를 가상으로 바꿔 판정하므로
  가로 핀(킹-폰-폰-룩) 사례가 자동으로 걸러진다.
- **승급**: 4가지(Q 우선), 캡처 승급 포함. 언더프로모션 테스트 포함.

## 8. Attack tables
- Leaper(폰/나이트/킹)는 테이블, 슬라이더는 **fancy magic bitboards**. 매직 넘버는 고정 시드 PRNG 로 시작 시 탐색
  (수 ms, 결정적). 외부 테이블을 복사하지 않아 라이선스 이슈가 없다.
- 대안: PEXT(BMI2) — x86 전용이라 이식성 때문에 보류, WASM/ARM 도 같은 코드 사용 가능. Kindergarten/Hyperbola 는
  느리다. 나중에 `Attacks::Magic::index` 만 교체하면 PEXT 로 바꿀 수 있다.
- 검증: 64칸 × 3000 점유에서 독립적인 ray-walk 와 비교.

## 9. Zobrist
- psq[16][64], castling[16](권리 비트별 키의 XOR), enpassant[8](조건부), side. splitmix64 고정 시드 → 플랫폼
  간 재현 가능. 64비트 키.

## 10. 합법성 판정과 Perft
- 의사합법 생성 → `legal()` 필터. 점유를 "수를 둔 뒤"로 가정하고 `attackers_to(king)` 를 검사(잡힌 기물은 제외).
  핀/체크 정보를 미리 계산하는 방식보다 단순하고 정확성 검증이 쉽다. 속도 병목이 되면 0.5 에서 핀 마스크로 교체.
- Perft: depth 1 은 bulk count. 디버깅은 `albatross perft N [fen]` 의 divide 출력을 다른 엔진과 diff.

## 11. CMake
`albatross_core`(STATIC) ← `albatross_uci`(STATIC) ← `albatross`(exe), 테스트는 `albatross_tests`.
`-DALBATROSS_SLOW_TESTS=ON` 으로 깊은 perft 를 CTest 에 등록. 경고: `-Wall -Wextra -Wpedantic` / MSVC `/W4`.

## 12. 구현 순서와 완료 조건 (모두 완료)
1. types/bitboard/attacks — ray-walk 대조 테스트 통과
2. zobrist/position/FEN — 왕복·거부 테스트, 키 일관성
3. move/movegen/legal — 캐슬링·앙파상·핀·승급·메이트/스테일메이트 테스트
4. make/unmake — 상태 복원 테스트
5. perft — 표준 6개 포지션 통과
6. 최소 UCI — uci/isready/ucinewgame/position/go perft/quit

## 검증 결과 (이 저장소에서 실제 측정)
- 단위 테스트 28개 통과 (GCC 13 Release, clang Release, ASan+UBSan Debug).
- Perft: 시작 포지션 depth 1–6 = 20 / 400 / 8,902 / 197,281 / 4,865,609 / **119,060,324**;
  Kiwipete d1–5, Position 3 d1–6, 4 d1–5, 5 d1–5, 6 d1–5 모두 참조값과 일치.
- `albatross perft 6`(시작 포지션): 1.36 s, 약 87M leaf/s (bulk count 포함이라 탐색 NPS 와 비교 불가).
  이 수치는 0.2 이후 탐색 NPS 의 근거가 아니다.

## 남은 일 / 알려진 한계
- `go`(perft 제외)는 첫 합법 수를 돌려주는 자리표시자다. 탐색은 0.2.
- Chess960, 3중 반복의 UCI 처리, `go` 시간 옵션은 미구현.
- `setoption` 은 받기만 하고 무시한다(옵션 없음).
